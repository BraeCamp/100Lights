# Database migrations

## What this replaced

Before this directory existed there was no migration system. The schema was
*emergent*: about 40 differently-named `ensure()` / `ensureTable()` /
`ensureSchema()` functions scattered across `lib/` and `app/api/` ran
`CREATE TABLE IF NOT EXISTS` and `ALTER TABLE` on first use — 72 creates and 46
alters in total. `db/schema.sql` described 8 of those ~70 tables and had long
since drifted; five tables were defined in both places, verbatim copies that
nothing kept in sync.

Three consequences, all of which this directory fixes:

1. **A fresh environment could not be built from the repo.** `projects`,
   `subscriptions` and `usage` — the three most important tables in the product
   — had no `CREATE TABLE` anywhere in the application code, only `ALTER`s that
   assumed they already existed. Their sole definition was the stale
   `db/schema.sql`. Staging, disaster recovery, a new contributor's local
   database: none were reproducible.

2. **Nobody could review or roll back a schema change,** because schema changes
   arrived as DDL buried in request handlers rather than as reviewable files.

3. **Every cold start paid for the DDL.** The `ensure()` memo flags are
   per-process, so on serverless each new container re-ran them — and per the
   project's own performance notes the real Neon cost driver is
   queries-per-cold-start.

## Layout

```
db/
  migrations/
    0001_baseline.sql   generated; the whole schema as of the cutover
    README.md           this file
  schema.legacy.sql     superseded; kept only because it is still the sole
                        definition of projects/subscriptions/usage
scripts/db/
  extract-schema.mjs    regenerates the baseline from any runtime DDL still in the tree
  migrate.mjs           the runner
```

## Commands

```bash
set -a && source .env.local && set +a   # migrate.mjs needs DATABASE_URL

npm run db:status      # what is applied, what is pending
npm run db:migrate -- --dry-run
npm run db:migrate     # apply pending migrations
npm run db:verify      # diff the live schema against the migration files
npm run db:extract     # regenerate 0001_baseline.sql from runtime DDL
```

Each migration runs inside its own transaction and is recorded in
`schema_migrations` by filename. Migrations are **append-only**: never edit a
file that has already been applied anywhere — add a new numbered one.

The runner uses `pg` rather than `lib/db.ts` because migrations need real
multi-statement transactions, which the Neon HTTP driver does not provide.

## Verification already done

`0001_baseline.sql` was applied to a throwaway PostgreSQL 17 instance:

- applies cleanly to an empty database
- produces all 72 tables
- is idempotent — re-applying is a clean no-op
- `pgvector` must be installed first (`track_embeddings.embedding` is
  `vector(512)`); the migration creates the extension itself, but the extension
  must be *available* to the server

Statement order is load-bearing and was established by that run:
extensions → tables → alters → indexes. Indexes come last because several index
columns (e.g. `affiliates.tax_token`) are added by the alters.

## Cutover — this has NOT been done yet

The runtime `ensure()` functions are still in place and still create the schema.
Nothing about the running application has changed. Do this when ready:

**1. Check the generated baseline against production.** It was generated by
reading code, and verified against an empty database — not against your live
schema. Compare them:

```bash
set -a && source .env.local && set +a
npm run db:verify
```

This lists tables that exist in one and not the other. Investigate every
difference before continuing. `project_admin` is a known extra in production: it
was created by `lib/project-admin-store.ts`, which had zero importers and has
been deleted, so nothing reads or writes that table any more.

**2. Record the baseline as already applied.** Production already *has* this
schema, so the baseline must be marked applied without running it:

```sql
INSERT INTO schema_migrations (version) VALUES ('0001_baseline.sql');
```

(On a genuinely fresh database, run `npm run db:migrate` instead.)

**3. Turn off the runtime DDL.** Set `SCHEMA_MANAGED=1` in the environment.
Every guarded `ensure()` then returns immediately — see `lib/schema-guard.ts`.
All 57 files containing DDL are guarded, so this switches off all of it at once.

**4. Watch a deploy.** If anything is missing, unset `SCHEMA_MANAGED` and the
old behaviour returns immediately. That one variable is the whole rollback.

**5. Once stable,** delete the `ensure()` functions and their call sites,
delete `db/schema.legacy.sql`, and remove the `LEGACY` block from
`extract-schema.mjs` — folding `projects`/`subscriptions`/`usage` permanently
into the baseline.

## Adding a migration

```bash
cat > db/migrations/0002_short_description.sql <<'SQL'
ALTER TABLE projects ADD COLUMN IF NOT EXISTS archived_at TIMESTAMPTZ;
SQL
npm run db:migrate -- --dry-run
npm run db:migrate
```

Do not add new `CREATE TABLE` / `ALTER TABLE` calls to request handlers.
